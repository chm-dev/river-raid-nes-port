# BUGS
Found in the milestone 1 playtest (`roms/m1_jet.gb`, 2026-10-31). All expected at this stage; not blocking.
- [x] **Player shot is invisible** (fixed in m2_hud: logic OAM had 40 slots, the shot is slot 47; now 48 packed into 40) - was: (it still destroys enemies). Likely the shot sprite's tile or palette; sprites are not yet set up for GBC. See `player.c` shot slot 47 and `entities_shot_tile()`.
- [x] **Enemy sprites are black** (m2_hud sets RGB sprite palettes in `gbc/main.c`; no generator change yet) - was: (size and direction are right). Entity palettes still hold NES values; `tools/gen_entity_gfx.py` needs GBC palette output, then `set_sprite_palette` for them. Milestone 3 colour work, earlier if cheap.
- [x] **Shots destroy enemies with a delay.** (fix built: `player_update_shot` now steps and tests the shot once per elapsed frame, 6 px each, instead of one 12 px jump; confirm in play.) Seen in the m2 playtest (shot and enemy colours confirmed fine): usually feels off, sometimes fine, as if the hit logic lagged the visuals. Suspect the 30 Hz logic (player/shot/collision every 2nd frame) against the 60 Hz scroll and sprite draw; the shot moves 6 px x ticks per logic pass, so it jumps 12 px and may be tested a frame after it is drawn. Check the shot/entity order and whether entities_hit_shot uses the same positions that are drawn before changing LOGIC_FRAMES.
- [x] **Some side hills and trees glitch.** No longer reproduces (2026-11-01): it must have been fixed by some earlier change; the cause was never found. `tests/host_river.ps1` passes on all four start levels (the host stub `tests/host/gb/gb.h` was added to make it build again). Was: not diagnosed; suspects: the unsplit tile job and the direct upload path writing while the display is on, or margin handling now that `RIVER_LEFT_COL` is 0. Check with `tests/compare_tile_rows.mjs` / `tests/host_river.ps1` before guessing.
- [x] **Stutter at fast speed.** Confirmed OK in play (2026-11-01). Cause: the loop ran at ~30 Hz at fast speed (0.51 passes per frame), mostly from `oam_camera` (31k units per pass). Fixed with 8-bit math: ~0.75 passes per frame at fast, 1.00 at cruise. `river_run_job` is also split (`RIVER_JOB_COLS` 10). Fast is still not a steady 60 Hz; further levers are in `HANDOFF.md`.
- [x] **Random entities remain and appear on screen** (suspected cause, fix built: on overrun passes the main loop always took the player branch and `entities_update` starved; now it runs at least every 2nd pass. Same for the next two.)  
- [x] **Death animation gets very slow when scene becomes busy**
- [x] **Enemies move very slow and stutter a lot**
- [x] **Pause menu is broken. Is invisible only letter "IT" can be seen** It still is usable if you navigate blind. Cause: the menu letters use logic OAM slots 56..63 but `gbc_logic_oam` had only 48 slots, so they were written out of bounds and never drawn (only slots 2..4 showed). Fix: `LOGIC_OAM_SLOTS` 64 in `src/gbc/main.c`. Follow-up: the menu sat too high (rows at screen y -1 and 15) and its X followed the camera. Now centred on the 160x144 screen: `oam_camera()` copies the menu slots (56..63, 2..4) untranslated while paused, and `src/player.c` uses hardware coordinates for them (GBC only). Follow-up 2: the cursor (plane icon, slot 2) was invisible. Its tile `HUD_LIFE_TILE` is uploaded only by the NES `hud.c`; the GBC HUD keeps its plane in the window tiles, so the sprite tile stayed blank. `player_init_graphics()` now uploads the `$5C` glyph to it on GBC (yellow, like the letters).
- [x] **Scroll camera before start of the gameplay, when river scrolls down should be aligned vertically with the position where plane will appear** currently it is bit off and gets aligned only after plane appears. Cause: the camera followed `player.x`, which stays at `PLAYER_START_X` during WAIT and jumps to the river centre only when `player_center()` runs, so the view then panned (2 px/frame). Fix: in WAIT, `camera_follow()` (`src/gbc/main.c`) aims at the river centre on the spawn row (`PLAYER_START_Y`), the same target `player_center()` uses. Follow-up: the X where the jet died carried into the next scroll-in and the attract screen. `camera_follow()` now snaps `camera_x` to the centre (`GBC_CAM_CENTER` = 16) when `player_state` changes to WAIT or ATTRACT (no easing), attract holds the centre, and WAIT then aims at the spawn-row river centre as before. Follow-up 2 (the snap did not help): in WAIT the target fell back to `player.x` (death X, or 120 at boot = camera 12) until the spawn row was non-black, which happens only ~17 lines before the jet appears, so the scroll-in eased back to the death X and straightened late; attract's 16 was 1 px left of the level-1 spawn view (17). Fix: the jet spawns on a fixed ring slot (`RIVER_SPAWN_SLOT`, the third tile row after a river start; the slot at `player.y` moved 3 px off when the scroll-in overshot by 7+ px) and `camera_follow()` latches the camera for that slot's centre in ATTRACT and WAIT as soon as it is generated (view still black), re-read after every river restart; READY snaps, easing only from PLAY on.
- [x] **Flash after hitting bridge with tank on it is not present** Cause: `ent_water_color()` in `src/entities.c` wrote NES palette entries through a macro that is a no-op on GBC (the river uses BG palette 0 there). Fix: a `__SDCC_sm83` branch rewrites BG palette 0 (water = colour 3) with `set_bkg_palette`, alternating water blue and dark red for 23 frames as on the Atari.
- [x] **Road color should be gray and is green** Cause: the GBC river had one BG palette (0), so road rows (already tracked as `ROAD_PALETTE` for the NES attribute table) drew in land green. Fix: BG attribute map (VRAM bank 1) per map row, written in `river_emit_stripe` when the row palette changes; palette 3 = grey road + yellow line (`src/gbc/config_gbc.h`, loaded in `gbc/main.c`).
- [x] **Grass color does not alternate between bridges** Cause: same single palette; the existing `river_land_alt` flip had nothing to select. Fix: palette 0 = dark green, palette 2 = bright green, chosen per row by the same attribute write. `ent_water_color` (bridge flash) now rewrites water in all three river palettes.
- [x] **Plane's projectile should be 1px in width (is 2px)** [All platforms] Cause: the shot tile in `tools/gen_entity_gfx.py` drew columns 3..4 (`0x18`). Fix: draw column 3 only (`0x10`), regenerated `src/entity_gfx.c`; sprite x offset and the 2 px hit box are unchanged. Follow-up: the bar looked about 2 px left of the nose. The jet tile's nose is column 4 (`0x08`, symmetric about column 4) but the bar was drawn at column 3 (`shot_x - 3`). Draw offset is now `shot_x - 2` (bar at jet x + 4); hit box unchanged.
- [x] **One of the side hills / trees colors are off.** There are 3 separate variants of riverside objects. One has a yellow color - this should be changed to brown if possible or some darker one. 
- [~] Enemies and fuel is dissapearing too early as they scroll. You can see it dissapear close to the bottom line near the hud. Cause: sprite cull/despawn kept the NES threshold (logic Y 232), but the GBC view reaches 239, so the last 8 lines were hidden. Fix: `ENT_CULL_Y` (232 NES, 240 GBC) in entities.c and `oam_camera`. Awaiting play-test.


# FEATURES
- [x] **Move the jet lower on screen.** The view is bottom-anchored (`GBC_VIEW_TOP_SCANLINE` 112), so only the jet's logic Y can move it: `PLAYER_START_Y` is 222 on GBC (was 218; sprites at y >= 232 are culled, so 222 is the limit). It also sets reaction time, the plan's main risk. If 4 px is not enough, thin the HUD Window (16 px) for look-ahead.
- [x] **Bank 0 headroom.** Done: `player.c` moved to bank 2; bank 0 now has ~2.6 KB free (see HANDOFF).
- [ ] **Sprite Y may be 1 px off** (NES draws at `y+1`). Check against the Atari after the jet is lowered. (Analysis 2026-11-01, inconclusive, no code change: `oam_camera()` draws logic OAM Y at view line `y - 112`, i.e. the sprite top is on scanline `y`, while the NES hardware put it on `y+1`. So GBC sprites sit 1 px higher than the NES relative to the river, which maps scanline S to view line S-112. Collision probes use logic Y unchanged. The Atari docs/disasm give no jet-row-vs-river pixel reference, so only a live Altirra capture of the jet top scanline against a river edge can say which is right. If it shows the NES `+1` is needed, change `y + 8u` to `y + 9u` in `oam_camera` and relax the `ENT_CULL_Y`/view-range tests by 1.)
